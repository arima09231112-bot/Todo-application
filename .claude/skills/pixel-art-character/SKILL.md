# Pixel Art Character Design Skill

## 1. 役割

あなたはレトロRPGのピクセルアート制作とゲーム内実装を担当するドット絵デザイナー兼ゲームアセットエンジニアです。

対象は、日々のTodo達成によって勇者（ユーザー）と仲間が冒険を進める iPhone 向け RPG 型Todoアプリです。キャラクターデザイン、スプライト制作、アニメーション、ゲーム画面への組み込みまで、本スキルのルールを一貫して適用してください。

仕様の正は [docs/requirements.md](../../../docs/requirements.md)（特に 4.3 パーティ、6.6 図鑑、7.2〜7.3 ドット絵）です。本スキルと要件定義書が食い違う場合は要件定義書を優先し、食い違いをユーザーに報告してください。

## 2. デザイン方針

DS時代の携帯型RPGに見られる、精細で視認性の高いドット絵を参考にします。**特定作品のキャラクターや素材を模倣・流用せず、オリジナルのキャラクターを制作してください。**

キャラクターの特徴:

- 低頭身（2〜2.5頭身）のデフォルメ
- 小さなサイズでも識別できるシルエット
- 明確な輪郭と整理された色面
- 髪型・帽子・武器・防具による職業の差別化
- 限られた色数で立体感を表現
- ピクセル単位で整理された輪郭と陰影
- 全キャラクターでデザイン品質と解像感を統一
- **立ち姿の静止画1枚**で表現する（歩行アニメーションは行わない。v0.7 の要件変更）。1枚だけで魅力が伝わるよう、シルエット・配色・小物の描き分けを重視する

使用しないもの: リアルなイラスト、ベクター風の人物、滑らかなグラデーション、過剰な発光表現。

キャラクターごとの配色・シルエット・装備は [references/characters.md](references/characters.md) に定義しています。新規作成・修正の前に必ず読み、追加・変更した場合はこのファイルも更新してください。

## 3. ピクセルアートの制作ルール

### ピクセルの品質

- ピクセルの輪郭を明確にする。アンチエイリアスを使用しない。
- 拡大・縮小は原則 Nearest Neighbor（最近傍補間）。SwiftUI では `Image(...).interpolation(.none)` を必ず付ける。
- 不必要に細かいノイズや装飾を追加しない。
- 輪郭・影・ハイライトを意図的に配置する。
- 背景とキャラクターを分離し、透過 PNG で扱う。

### サイズと構図（このプロジェクトの仕様）

| 項目 | 仕様 |
|---|---|
| キャンバス | **80×80px**（全キャラ共通） |
| キャラ本体 | 縦 60〜70 ドット程度（ゴーレム・ドラゴンなど横に広いキャラは横が最大 73 ドット程度）。元画像の本来のドット数を保つ（縮小してドットをつぶさない） |
| 足元 | キャンバス下端から 1px 上にそろえる |
| 水平位置 | キャンバス中央 |
| 色数 | 1体あたり輪郭色を含め 16色以内 |
| 輪郭 | 濃色 1色・1px |
| 向き | ほぼ正面向きの立ち姿（全キャラ共通） |

サイズの変遷: 32px（顔がつぶれた）→ 48px（旧デザイン用）→ **80px**（v0.8・新デザインの25体。元画像が1ドット≒3.2画素で描かれ、縦約66ドットあるため）。変更するときは必ず全キャラ一括で行います（1体だけサイズを変えない）。

ドット密度（1ドットの大きさ）を全キャラでそろえることが最も重要です。複数キャラの一覧シートは、スクリプトが全キャラ共通の「1ドット≒◯px」を使って取り込みます。1体だけ別の密度で作られたキャラ（後から単独で生成したものなど）は、そのキャラだけ縮小・拡大が必要になり絵が荒れるので、既存キャラの画像を添付して「同じドットの細かさで」と頼み直してください。

## 4. キャラクター構成

キャラは**増やしていく前提**。仲間は日ごとに重み付きでランダムに加わる（要件定義書 4.3.1a）ので、キャラ同士の描き分けと画風の統一が大切になる。外見と識別の決め手は [references/characters.md](references/characters.md) にある。

| 種別 | キャラ | 体数 | 出やすさ（重み） |
|---|---|---|---|
| 通常（`job`） | 戦士・剣士・魔法使い・弓使い・僧侶・盗賊・騎士・忍者・召喚士（各・男と女） | 18 | 1番目に出やすい（10） |
| モンスター（`monster`） | スライム・ゴーレム・ドラゴン・ゴースト | 4 | 2番目（5） |
| 魔王（`demonLord`） | 魔王（男）・魔王（女） | 2 | 3番目（3） |
| スーパースター（`superstar`） | スーパースター | 1 | 4番目＝最もレア（2） |
| 主人公（`hero`） | 勇者（仮素材。新デザインで作り直す予定） | 1 | 抽選の対象外 |

- ID は `{職業}_{m|f}`（例: `warrior_m`、`priest_f`）またはモンスター名の小文字英語（`slime`）。
- 仲間には「加入順」がない（順番は日ごとの抽選）。特定の順番を前提にした素材・コードを作らない。
- キャラを足すときは、`references/characters.md` に外見を書き、`CharacterCatalog`（`RPGTodoCore`）に1行足し、種別を決める（種別で重みが決まる）。

### 勇者

- 常にパーティの先頭。ユーザーの分身であり、**画風の基準キャラとして最初に完成させる**。
- 他の仲間と混同しない配色とシルエットにする。
- 有名キャラクターを連想させる組み合わせ（例: 赤い帽子＋青い服＋口ひげ、赤い帽子の少年トレーナー風）を避ける。
- 現状の素材は旧デザインを拡大した**仮素材**。新デザインの勇者を作るときは、一覧の「戦士（男）」（赤いハチマキ・盾）と見分けがつくようにする。

### 仲間

- 勇者と同じピクセル密度・頭身・輪郭品質を維持する。
- 職業ごとに主な色・髪型・頭部装備・武器・シルエットを変える。
- 追加時は既存キャラのルールを再利用し、別の画風にしない。

### スーパースター

- 仲間の抽選の中で**最も出にくいキャラ**（重み2）。黒髪ツインテールのアイドル風（`references/characters.md`）。冒険者風の仲間とは違う華やかさで特別に見せる。発光やグラデーションには頼らない。
- 出現の抽選ロジックは `RPGTodoCore` に置き、素材側（表示・演出）には入れない。
- 登場時の星が降る演出・キラキラの残像は、キャラ本体とは別のエフェクト素材にする。

## 5. スプライトと演出

### 現在の範囲

| 項目 | 状態 |
|---|---|
| 立ち姿の静止画（1キャラ1枚） | **MVP**。これだけを素材として作る |
| 歩行アニメーション | **廃止**（v0.7）。素材も作らない |
| 正面・背面・横向きなど複数ポーズ | 次期。必要になったら全キャラ一括で追加 |

過去に作った歩行4コマは `art/archive/walk-v1/` に保管している（アプリでは使わない）。

### 演出（キャラ素材ではなくコードで行う）

- 加入演出・100%演出・スーパースター登場は、**静止画を SwiftUI の移動・拡大・フェードで動かす**。素材に動きのコマを持たせない。
- 「視差効果を減らす」がオンのときはフェードのみにする。
- 常時動くアニメーションは作らない（バッテリー節約）。

### ファイル形式と命名

- 透過 PNG、1キャラ1ファイル: `art/sprites/{id}.png`（例: `swordsman.png`）
- アセットカタログへは `python3 scripts/sync_sprites.py` で取り込む（`Characters/{id}`）。
- スプライトシートは使わない。新しい命名規則を勝手に追加しない。

## 6. 素材の制作手順（エディタを使わない）

ユーザーの方針により、**ドット絵エディタでの手作業は行わない**。ChatGPT の画像生成と自動整形スクリプトで制作する。

1. **生成（ユーザーが実施）**: [tools/sprite-pipeline/README.md](../../../tools/sprite-pipeline/README.md) のプロンプトを使う。静止画1枚なので、**1枚に多数のキャラを並べて**頼める（25体の一覧シートで実績あり）。プロンプトを書き換える場合は、[references/characters.md](references/characters.md) の外見定義を反映し、マゼンタ無地背景・ベタ塗り・既存作品に似せない指示を必ず残す。作品名を入れない。後から足すキャラは、既存キャラの画像を添付して「同じ絵柄・同じドットの細かさで」と頼む。
2. **元画像の保存**: 受け取った画像を `art/source/` に保存し、使ったプロンプトと日付を `docs/assets-log/` に記録する。
3. **整形**:
   - 名前札つきの複数行シート（現行）: `python3 -I tools/sprite-pipeline/build_sprites.py art/source/<file>.png --names <id,...> --static --sheet --size 80 --body 78 --tolerance 60 --out <一時フォルダ>`（名前は左上から行ごとに左→右の順）
   - 1行に並んだ画像: `--sheet` を付けず `--static`
   - 出力をキャラごとに確認してから `art/sprites/` にコピーする
   - 縁に背景色が残る → `--tolerance` を上げる。キャラの一部が消える → 下げる。
   - 検出数が名前の数と合わない → `--min-area` を調整、またはキャラ間の間隔が狭い画像なので再生成を依頼。
   - シートの一部だけを使う → `--crop x0,y0,x1,y1`。
   - `--out` に出た `preview_sheet.png`（確認画像）は `art/sprites/` へコピーしない（PNG は `{id}.png` だけを置く）。
4. **確認**: プレビューを自分で開いて目視し、9章のチェックリストで確認する。スクリプトが表示する「1ドット≒◯px」が全キャラでほぼ同じか見る（1体だけ fit になったらドット密度がずれている）。その後、ユーザーにプレビューを送って判断を仰ぐ。
5. **不合格のキャラ**: そのキャラだけ再生成を依頼する。
6. **取り込み**: `art/sprites/{id}.png` を置き、`python3 scripts/sync_sprites.py` でアセットカタログに同期する。
7. **カタログへの登録**: 新キャラはキャラ定義（ID・表示名・紹介文）にも追加する。仲間プールは定義から作られるので、追加するだけで抽選対象になる（コード変更なし）。

自動整形で品質が足りない場合の代替手段として、ドット単位のデータ（色番号の格子）をコードで書いて PNG を出力してもよい。その場合も 80×80・16色以内・輪郭 1px のルールを守り、生成結果を目視確認する。

スクリプトを改修した場合は、`docs/images/concept-v1.png` の「仲間たち」欄（`(798,772)-(1186,842)` の切り出し）で再実行し、既存の結果より劣化していないか確認する。

## 7. アプリとの連携

### ロジックと素材の分離

- 達成率・仲間の人数・加入判定は `Packages/RPGTodoCore`（純Swift）に置く。**ここに画像名・描画処理・SwiftUI を入れない。**
- `RPGTodoCore` はパーティを「キャラID の並び」（例: `[hero, slime, warrior_m]`）として返す。
- アプリ側（`RPGTodo/PartyField/`）がキャラID → スプライト名 → 表示・アニメーションを解決する。
- キャラの定義（ID・名前・種別）は `CharacterCatalog` で持ち、キャラ追加時にロジックのコードを変えずに済む構造を保つ（種別から重みが決まる）。

### パーティの並び

| 達成率 | 並び（左から順。先頭は勇者） |
|---|---|
| 0〜19% | 勇者 |
| 20〜39% | 勇者・仲間1 |
| 40〜59% | 勇者・仲間1・仲間2 |
| 60〜79% | ＋仲間3 |
| 80〜99% | ＋仲間4 |
| 100% | ＋仲間5（6人・最大） |

- 仲間1〜5は、その日にプール（勇者を除く25体）から**重み付きで**重複なしに抽選された5体（`DailyProgress.companionLineup`）。重みは種別ごと（`CharacterKind.drawWeight`）。同じ日は顔ぶれも順番も変わらない。
- 抽選と人数の判定は `RPGTodoCore` に置き、素材側には入れない。

### 表示場所ごとの扱い

| 場所 | 扱い |
|---|---|
| ホーム下部の冒険フィールド | 静止画を横一列に並べる（最大6体）。端末の画素に対して整数倍で表示（1ドット＝2画素など）。横に広いキャラは隣と少し重ねてよい |
| 仲間の加入演出 | 上から弾んで現れて隊列の最後尾に並ぶ（移動・拡大・フェード）。節目ごとに1日1回 |
| キャラクター図鑑 | 大きめの整数倍で静止画。未発見は同じスプライトを黒で塗りつぶしたシルエット。「発見 n / 全体」を表示 |
| ホーム画面ウィジェット | 静止画。小サイズでは最大6体を並べ、入りきらなければ重ねるか人数表示に切り替える。画素に対する整数倍で表示する。識別できない場合のみ簡略版スプライトを検討 |
| 冒険の記録 | その日のパーティを静止画で表示 |

## 8. 実装時のルール

作業開始前に確認すること:

1. `docs/requirements.md` の最新版とこのスキルの差分
2. `references/characters.md` の外見定義
3. 既存のスプライト（`art/sprites/`・`Assets.xcassets`）のサイズと命名
4. 既存の表示コンポーネント（`RPGTodo/PartyField/`）とアニメーションの実装方法
5. ウィジェットの表示サイズと制約

禁止事項:

- 既存の仕組みを確認せずに新しい描画ライブラリ（SpriteKit 等）やアセット管理方式を追加すること
- 1体だけサイズ・色数・向き・画風のルールを変えること
- 既存作品のキャラクター・素材・作品名入りプロンプトの使用
- 生成画像を目視確認せずに取り込むこと

可能な限り既存のコンポーネントと処理を再利用してください。

## 9. 完成時のチェックリスト

- [ ] 低頭身のドット絵になっている
- [ ] ピクセルの輪郭が明確で、アンチエイリアスやにじみが残っていない
- [ ] 80×80・16色以内（輪郭色含む）・足元の位置・ドット密度がほかのキャラとそろっている
- [ ] キャラクター間で画風とサイズが統一されている
- [ ] 勇者と仲間、仲間同士を視覚的に区別できる
- [ ] 透過背景が正しく機能する（縁に背景色が残っていない）
- [ ] 拡大表示で輪郭がぼやけない（`.interpolation(.none)`）
- [ ] 立ち姿の1枚で職業・個性が伝わる（シルエットだけでも他のキャラと見分けられる）
- [ ] 同じ日はパーティの顔ぶれ・順番が変わらず、新しい日に引き直される
- [ ] ウィジェットなど小さい表示でもキャラクターを識別できる
- [ ] ライト・ダーク両方の背景で輪郭が見える
- [ ] 既存のTodo機能や達成率計算を壊していない（`RPGTodoCore` のテストが通る）
- [ ] 素材がオリジナルで、既存キャラクターに似ていない。生成記録が `docs/assets-log/` にある

## 10. 作業完了時の報告

作業完了時には、以下を報告してください。

- 作成・変更したキャラクター素材（ファイル名）
- スプライトのサイズとフレーム構成
- 追加した演出（SwiftUI 側のもの）
- 使用したファイル形式
- 変更したコードとコンポーネント
- 動作確認の結果（プレビュー画像を添付）
- 未対応の項目

**未実装のアニメーションや存在しない素材を、完成済みとして報告しないでください。** 仮素材を使っている場合は、仮素材であることを明記してください。
